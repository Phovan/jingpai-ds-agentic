# 劲牌企业大脑 Demo 战略、项目、系统及关联本体虚拟数据 V0.3

> 快照日：2026-09-18。用途：PMO / EngineeringOS User Story、交互原型和 Demo 的**虚拟数据底稿**，不是劲牌的项目台账、系统清单、经营指标或客户确认的战略文件。本文中的日期、数值、角色分派、问题、对话和结果全部为演示设定；即使名称与客户资料相同，也不表示其真实状态已获核实。不要用本文替代 `001-劲牌企业战略与目标-V0.1.0.md` 的客户确认流程，该文件仍为占位稿。V0.3 在 V0.2 对象档案上定向补充战略拆解、项目治理和系统工程信息。

## 1. 数据设计与 Demo 主线

本底稿遵循[产品设计通识原则](000-劲牌企业大脑产品设计通识原则-V0.1.1.md)、[PMO User Story V0.1.3](101-劲牌PMO项目管理提效场景UserStory-V0.1.3.md)、[EngineeringOS User Story V0.1.3](102-劲牌EOS产研运维提效场景UserStory-V0.1.3.md)和[UE/UI 规范 V0.1.2](201-劲牌企业大脑UE和UI设计规范-V0.1.2.md)。战略名称采用已讨论的五个建议名称；S01 是上位愿景，S02-S05 是直接承接方向，不把五项当作同级 KPI 相加。一个劲牌企业大脑共用对象和事实；PMO Agent 看项目、需求及跨项目影响，EngineeringOS Agent 看实现、发布及运行。已批准的目标、范围和生产发布始终由有权的人确认。

**一条完整演示链：** S02 / S05 → P02 评论区营销与消费者问题闭环 → X02 评论区营销系统。系统出现“待处理队列漏单”线索，Agent 引用日志和时间窗请系统负责人核实；确认为既有功能缺陷后，形成 I01 工程 Issue，并将可能影响项目目标的部分登记为 R01 风险。另一个“跨平台评论聚合”诉求不属于既有范围，先生成 D02 待澄清需求，不能混作缺陷。PMO 对项目影响与优先级作判断，EngineeringOS 跟进实现、独立审核和发布；业务 Owner 在观察期验证“原问题是否解决”，结果才回写战略贡献。

**其他演示入口：** 管理层从战略下钻项目组合（P02/P03）；PMO 查看 P02 与 P11 共用的风险；系统负责人从 X02 追问项目和版本影响；业务 Owner 追踪 D02；项目经理发起 P09 的立项草稿；员工核对周报；供应商只看被委托的 P06 工作包。多状态清单为上述旅程提供上下文，不要求在首屏把所有项目逐个演完。

### 1.1 数据契约

- 统一 ID：战略 `Sxx`、项目 `Pxx`、系统 `Xxx`、需求 `Dxx`、风险 `Rxx`、亮点 `Lxx`、组织 `Oxx`、员工 `Exx`、供应商 `Vxx`、报告 `Bxx`、承诺 `Cxx`、资料 `Fxx`、Release `RELxx`、Issue `Ixx`、Impl `Mxx`。同一对象跨 PMO 和 EngineeringOS **只用一个 ID**；现有 Demo 中的 `STR-DEMO`、`PRJ-001`、`SYS-01` 等为旧种子，不与本底稿 ID 默认等同，替换时须做显式迁移。
- 每个对象最少有：名称、业务目标/用途、责任角色、状态、更新时间、来源/证据、关联 ID、下一步、可见范围。目标值、实际值、预测值分别存储；无实测数据写“待采集”，不填 0。健康灯由口径和证据计算，不直接从一段聊天推断。
- **事实分级：** `演示源记录`、`Agent 待核实判断`、`责任人已确认事实`、`已批准决定`、`经业务验证结果`。每次升级都保存操作者、时间、依据和原版本。下文的演示数值仅是虚拟源记录；Demo 可模拟其核实过程，不能向客户表述为真实统计。
- 状态互不代替：项目“完成交付”不等于目标达成；系统“已上线”不等于需求“已解决”；Issue 关闭不等于风险关闭；报告生成不等于报告确认；材料同步不等于事实被认可。
- 以下范围与权限仅是演示规则。角色切换只改变可见对象及动作，不模拟真实客户授权；禁止让系统管理员因配置连接而拥有所有业务资料的阅读权。
- 第 9 部分新增的项目金额、工时、预测均为**虚构的项目组合演示样本**，不是数说报价、劲牌预算或真实成本；单位“万元”仅用于展示预算基线与偏差，1 人天按 8 工时作演示换算。准备立项项目只能有估算区间，不能显示批准预算或虚构实际花费；预测值也不自动改批准基线。

**关系与动作：** `S01 → S02/S03/S04/S05` 为方向分解；`S02 → P02` 为直接承接；`P02 → X02` 为建设/使用依赖。管理层可以追问“哪些项目支撑 S02、依据何在”，也可以确认调整建议；Agent 只能形成带来源的候选关系，不能自行改写战略目标或夸大贡献。若 X02 的 73% 受漏单影响，大脑必须将 S02 对应指标标为待复核，并提示可受影响的 P02，而非展示绿色达标。

### 2.1 从愿景到收益的拆解规则

参照战略地图的“战略目标→衡量指标/目标值→战略举措”及 PMI 收益实现管理的“战略→项目交付→持续收益”逻辑，Demo 为每项方向保存五层关系：**上位意图 → 可负责的细分目标 → 领先/结果指标与基线 → 项目或经营举措 → 由业务 Owner 验证的收益**。方向之间可以互相支撑，但不能把同一项目成果在多个战略下重复加总。结果指标未到观察期时只显示过程进展，不宣称收益已实现。方法参考：[Balanced Scorecard Institute 战略地图](https://balancedscorecard.org/bsc-basics/what-is-a-strategy-map/)、[PMI 收益实现管理指南](https://www.pmi.org/standards/benefits-realization)。

| 方向 | 第二层：演示细分目标 | 第三层：领先/结果信号 | 第四层：关键举措及项目 | 第五层：收益责任与验证节点 |
| --- | --- | --- | --- | --- |
| S01 百年企业愿景 | S02 产品与用户、S03 友好经营、S04 国际品牌、S05 数智生产力持续形成能力 | 不设伪“愿景完成率”；看各方向是否有经验证的结果和重大底线风险 | 由 S02-S05 承接，不单设一个“愿景系统” | E01 管理层周期复盘方向组合、冲突及长期约束。 |
| S02 极致产品力与性价比 | 消费者问题被及时处理；原料与生产问题可追溯 | 领先：4 小时内分派率（P02，73% 待复核）；结果：问题实际解决、抽样批次追溯通过 | P01/P02/P04/P05；P03/P06 提供经营和供应链支撑 | E05/E07 按问题观察期和抽样批次验收；不能用“评论已分派”替代消费者问题解决。 |
| S03 四个友好 | 本 Demo 仅拆员工学习和供应商协同两个待客户确认的子方向 | 领先：实训完成率、交期变更回执完整率；结果：方法复用效果、供应商协同改善 | P06/P08；P07 待立项，P02/P05/P10 体现相邻影响 | E11 验证 L01 是否减少返工，E06 验证异常提前反馈是否改善；其余“友好”定义待客户补充。 |
| S04 品牌出海 | 先验证目标市场洞察，再验证品牌内容与渠道试单 | 领先：市场资料有效性与审批；结果：2 个市场的用户/渠道验证结论 | P09 是 P10 的前置；X10 仅为拟建平台 | E10 先批准市场和试点门槛，取得样本及试单证据后才判结果；准备立项不写“出海达成”。 |
| S05 数智化与 AI 生产力 | 项目风险提前被看见；需求从受理到业务验证不断链 | 领先：风险提前识别率 41%、需求可追踪率 54%；结果：处理时效、返工减少和使用效果 | P11 PMO Agent 与 P12 EngineeringOS Agent 共用 X12，一期以 P02/X02 打样 | E02/E04 核对过程事实，E05 验证问题解决；仅对试点样本陈述收益，不外推全集团。 |

**演示追问：** “P02 对 S02 的贡献是什么？”先返回目标、指标口径、X02 事实和 F01 数据质量警告；再区分“按期分派”与“消费者问题解决”。“是否应调整 P02？”展示继续修复/扩大 D02/保持范围三种方案的资源与收益假设，由 E01/E05 决定；大脑只保存被确认的战略关联与贡献证据。
